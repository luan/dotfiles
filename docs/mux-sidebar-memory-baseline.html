  • Accepted prototype: tree rows now use shared Rc<str> session IDs. That already produced a large allocation win in build_items.
  • Rejected for snapshots: adding an interning table to the MessagePack snapshot. The largest measured live shape has only 2,956 duplicated string bytes, and an interning table would add format complexity, migration risk, and lookup overhead.

Daemon retained-state audit

The daemon's resident state is intentionally small: heavy metadata by session, short-lived agent activity caches, usage bar strings, and counters. Base tmux snapshots are temporary per tick; serialized snapshots are written to disk and not retained beyond the loop iteration.

meta: HashMap<String, SessionMeta>Heavy per-session branch/PR/process/agent/status dataRetain only live sessions; pruned every daemon tick

Accepted change: prune daemon metadata/activity caches for sessions no longer present in tmux before each snapshot. This prevents stale session metadata from living until the next heavy metadata refresh or activity grace expiry.

Multiple sidebar clients / duplicate per-process state

Each attached sidebar pane is a separate mux process, so terminal buffers, tree rows, selection/filter state, and current viewport state are necessarily duplicated per client. The daemon snapshot is the shareable boundary. Before this pass, daemon-backed sidebars also retained the decoded HashMap<String, SessionMeta> after tree rows had already been materialized, duplicating heavy metadata in every sidebar process. The optimized path now drops that decoded map immediately after building rows; direct/non-daemon mode still keeps metadata for skipped expensive refreshes.

Metadata refresh temporary allocations

Heavy metadata refreshes were audited for temporary allocation spikes in process-tree handling. The previous shape of the code built a parent_of map, cloned a full name_of map, and then rebuilt child indexes separately for CPU aggregation, memory/process detection, and agent detection. The optimized path builds one child index directly from the ps sample map, shares it across all three passes, reads process names from the sample map, and uses borrowed session keys for CPU/memory/process intermediate maps.

Dependency and binary footprint audit

Dependency features were audited for runtime-memory relevance before changing defaults. The only safe trim accepted here is chrono: disable crate defaults while keeping std and clock, which are required by mux status formatting. This removes unused chrono default feature surface such as oldtime/wasmbind without changing behavior.

Other large dependencies (ratatui, crossterm, sysinfo, serde/MessagePack) sit on active runtime paths. Since the binary/RSS measurement did not move materially, broader feature churn is deferred unless future profiling ties a specific dependency feature to startup RSS.

Immediate conclusions for the next tasks

  • The synthetic state-machine path has a roughly 11.1 MB RSS floor regardless of visible/hidden/animation work, so the next wins are likely structural allocations and retained data, not loop counters alone.
  • Active animation changes CPU/redraw work but does not change this process-level memory floor in the synthetic profile command.
  • No leaks were reported in the captured synthetic runs, so task k should focus on allocation counts/bytes per hot path rather than leak hunting.
  • Live tmux profiling is still required before claiming real-session memory headroom; that is intentionally left to task 4v.
